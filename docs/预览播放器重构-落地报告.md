# 预览播放器重构 · 落地报告

> 配套设计文档：`docs/预览播放器简化重构方案.md`
> 本报告记录**实际落地的代码**、每个决策的理由，以及哪些结论已经被机器验证、哪些还不能。

---

## 一、为什么"修好这个又冒出那个"

结论先说：**这不是"bug 比较多"，而是这套架构会持续生产 bug。**

诊断阶段定位到三个结构性原因，每一个都足以独立解释"修一个冒一个"：

### 1. 同一个"当前播放时间"有三个写者

| 写者 | 位置 |
| --- | --- |
| 全局时钟 | `GlobalTimelineManager` |
| 页面状态 | `Editor.ets` 的 `playheadSec` |
| 播放器回调 | `SingleTrackController` 的 `timeUpdate` → `onProgressChanged` |

三者靠**四层启发式**互相打补丁：阈值（`globalMs >= segEnd - 150`）、轮次号（`seekEpoch` / `lifecycleEpoch`）、拖拽 settle 窗口（260ms + 0.55s 容差）、段边界栅栏（`isBarrierSwitching`）。
每加一层，就多一个"什么时候该忽略对方"的判断题 —— 而这道题的正确答案依赖时序，时序又依赖设备。**这就是 bug 的产地。**

### 2. 事件回调里做异步 IO，绕过串行队列

`completed` 分支自己调 `loadSourceInternal(nextSeg.uri, 0).then(play)` 换段，`stateChange` 分支里 `player.reset() + fs.openSync()`。
这两处都不经过队列，于是同一个 `currentSegmentIndex` 有了两个写者，只能再加一个 `activeLoadedSegmentIndex` 去猜"到底装的是哪一段"。

### 3. 用超时掩盖竞态

`waitForSurface(1500)` / `waitPrepared(3000)` / `seekPlayer(2000)` / 模板就绪看门狗 `1800`。
超时不是修复，是**把竞态换成了偶发卡顿**：超时到了就往下走，于是"surface 还没来就设 fdSrc"、"prepared 还没到就 seek"。

### 4. 顺带挖出的一个真 bug（语义冲突）

- `CoreBridge.ets` 用**墙钟跨度**算时长：`durationSec = max(60, round((endTs - startTs) / 1000))`，而 `TRIP_GAP_THRESHOLD_MS = 120 * 1000` 允许行程中间缺 1~2 分钟。
- 旧预览却用**观察到的切片索引**当时间轴：`startMs = sliceIndex * 60000`。

后果：行程尾部 60~120s 没有任何 segment，而兜底分支 `return { segmentIndex: 0, offsetMs: 0 }` —— **播放头直接跳回行程开头**。
更严重的是分屏：若 Front 缺第 2 分钟、Back 有，同一时刻的两路画面会被摆到不同全局时间，**分屏播的不是同一时刻**，直接违背需求②。

## 二、新架构：三层，每层只有一个职责

```
纯函数层    TimelineMath / PreviewLayout     无状态、无 IO、无 @ohos 依赖 → 可离线测试
   ↓ 给定"模板 + 切片"，算出几何与"某时刻该播哪一段的哪一毫秒"
时钟层      TimelineClock                    唯一时间权威，唯一跳转入口
   ↓ 唯一的"现在在哪"
对账层      GlobalTimelineManager            协调器：把时钟位置分发给各轨
            SingleTrackController            幂等对账：只在必要时碰播放器
   ↓
            AVPlayer + XComponent(Surface)
```

### 核心思想：幂等

`SingleTrackController.reconcile(desired)` 的语义是「**请让播放器处于"第 90 秒、播放中、1.0 倍速"这个状态**」，而不是「执行一次跳转」。

对账器自己算出：该装哪个文件、该 seek 到哪一毫秒、该播该停。**重复调用无害** —— 状态已经对了就什么都不做。

这一个性质消掉了旧架构里绝大多数机制：

| 旧机制 | 为什么不再需要 |
| --- | --- |
| `seekEpoch` / `lifecycleEpoch` | 重复 seek 天然无害，不需要"丢弃过期的" |
| `seekToken` 去重 | 同上 |
| 拖拽 settle 窗口 + 0.55s 容差 | 拖拽期间时钟不推进，松手只 seek 一次 |
| 段边界栅栏 `isBarrierSwitching` | 段边界不是特殊事件，只是"位置变了"，重新对账即可 |
| `activeLoadedSegmentIndex` | 装的是哪一段由 `loadedUri` 唯一决定，无需猜测 |
| 4 个 `setTimeout` 超时 | 等待不是"等超时"，而是"事件到了就再对账一次" |
| 串行队列 + 静默 `return` | 并发靠 **latest-wins 合并**，不丢弃调用方 |

### 时钟层的三条不变式

`TimelineClock` 是唯一的时间权威：

1. **只有 `seek()` 能让播放头倒退。** `advanceFromMaster()` 只接受前进（`next <= playheadMs` 直接忽略）—— 这一条在时钟层就杀死了"被迟到的旧回调拽回去"。
2. **只有 seek 递增 `seekGeneration`。** 对账器靠它判断"这次需要强制 seek 吗"，不再靠时间窗口猜。
3. **拖动只改 `getVisibleMs()`，不改真实位置。** 松手时才 `seek()` 一次。

### 对账器的关键取舍

- **`timeUpdate` 在 seek / loading / 已播完期间不上报。** 这是防"迟到回调把播放头拽回去"的第一道闸门。
- **段间空洞不回退。** `segmentAt()` 在空洞处返回 `kind = GAP`，`gapHoldIndex()` 指向**上一内容段** → 冻结末帧；开头即空洞则黑场。**绝不跳回第 0 段。**
- **没人覆盖的时刻要跳过，不能僵住。** 若某一分钟只有模板之外的机位录到（例如 T2 用 Front/Left/Right，而该分钟只有 RightFront 有文件），所有轨都只能保持上一帧，**没有任何轨能驱动时钟**。协调器用 `isCoveredMs()` / `nextCoveredMs()` 识别并跳过。网格由**全部机位的全部切片**建立，因此时间轴总时长在切模板时保持稳定。

## 三、需求逐条对应

### ① 拼接多画面（多机位分屏）

- 布局唯一来源：`Models.ets` 的 `TEMPLATE_DEFINITION_MAP`（含 `canvasWidth` / `canvasHeight`），由 `PreviewLayout.buildSlotGeometry()` 读取。
- **几何由原生导出契约反推并锁定**：`export_engine.cpp:83-89` 的 `kNativeTemplateContracts` 是"导出真相"，离线测试逐条比对 ArkTS 侧画布尺寸与 `needSideTrack` / `disableFrontAudio`。
- **修正了一个真实的预览/导出一致性 bug**：T4 横向三分屏，`Models.ets` 原写 `0.3333/0.3334/0.3333`，而原生是 `crop=960:1080` + `scale=1920:1080` + `crop=960:1080` → `hstack` ⇒ **`0.25/0.5/0.25`**。预览过去与导出不一致，现已对齐（左右两栏由 1/3 宽改为 1/4 宽并横向放大 2 倍）。
- 槽位**常驻 3 个**，`controller` 身份终身绑定 `slot_0/1/2`，切模板只改机位与段 —— **XComponent / Surface 永不重建**（旧版把 `activeTemplateId` / `switchTaskId` 编进 `ForEach` key，靠"key 变了就重建"来让几何生效，代价就是 Surface 重建 + 一整套追踪重建的状态机）。

### ② 拼接多个视频、统一视角延续

- **墙钟网格 `TimeGrid`**：`sliceCount = max(1, round((max - min) / 60000) + 1)` —— **中间缺失的分钟仍占一个槽位**。
- 因此同一时间戳在不同机位的段序列里 `index` 可以不同，但**落在同一全局时刻**（测试用例 `buildSegmentSpans: 机位各自缺不同分钟时，同一时间戳仍落在同一全局时刻` 断言两路 `offsetMs` 均为 5000）。
- 换段不再由 `completed` 事件里的异步 IO 完成，而是"时钟往前走 → 重新对账 → 发现该换文件 → 换"。段边界不再是特殊事件。

### ③ 拖拽

- 拖动期间时钟 `dragging = true`，`getVisibleMs()` 返回预览值，**真实位置不动**，对账器直接 return（完全不碰播放器）。
- 松手：一次 `seek()`，`seekGeneration` 递增一次。
- **`seekToken` + `playheadMs` 合并为 `PreviewSeekRequest`**（`AppState.ets` 的 `token` + `targetMs` 同一对象）。旧版用两个独立 `@Prop` 表达"跳到哪里"，而 `playheadMs` 同时又被播放推进改写，二者更新顺序不受 ArkUI 保证 → "新 token 配旧位置"错跳，只能靠 260ms settle 窗口掩盖。

| 真机运行 / 渲染 | ❌ **无设备，未验证**（`hdc list targets` 为空） |

### 离线测试为什么重要

`TimelineMath`（网格 / 分段 / 空洞）与 `PreviewLayout`（几何 / 宽高比 / 时钟主轨选择）是**纯函数、无 `@ohos` 依赖**，因此可以在 Node 里直接跑。
测试用例本体只写一份（`*Cases.ets` 不 import hypium），设备端 hypium 包装器与离线 harness 共用同一份断言 —— **不会出现"两套断言各自漂移"**。

这套测试在本次重构中**真的抓到了 bug**：最初用"观察到的切片去重"当网格，测试立刻暴露"缺一分钟时同一时刻的两路画面被摆到不同全局时间"。

## 六、残留风险与未验证项（诚实清单）

1. **真机渲染完全未验证。** 所有 UI 层面的行为（XComponent 是否真的不重建、遮罩位置是否精确、`.aspectRatio` 下的 letterbox 映射）只有编译期保证，**没有一台设备跑过**。
2. **T4 的 crop 侧别与原生仍有细微差异。** 原生左槽取 LeftFront 的**右半**、右槽取 RightFront 的**左半**；预览用的是**居中 2 倍裁切**。曾尝试加 `cropStartX` 精确对齐，但 `.position({x: '-N%'})` 的百分比基准语义在 Stack 内**无法在没有设备的情况下验证**，为避免引入可见回归而**主动回退**，只在 `Models.ets` 的 `zoomX` 注释里记录了这处已知差异。
3. **`hideGps` 原生根本不使用。** `export_engine.cpp:178` 的 `buildFrontPrivacyMaskChain(hideSpeed, hideVin, hideTime)` 只有 3 个参数，所有调用点都只传这三个。预览侧因此也只用 `hideTime`（旧代码的 `hideTime ?? hideGps` 恰好等价于 `hideTime`，是个无意的 no-op）。`hideGps` 仍保留在导出请求结构里以兼容既有契约。
4. **`EditorPreviewArea` 的 `@Watch` 自守卫是防御性的。** ArkUI 不保证 `@Watch` 只在值变化时触发（父组件重渲染也可能再次派发），因此每个处理器都先与"已生效的值"比较。这在没有设备的情况下**无法验证必要性**，但它使组件对"框架多叫几次"免疫 —— 代价是几行比较。
5. **签名 `.p12` 缺失**，无法产出可安装的 HAP（既有问题，与本次重构无关）。

## 七、怎么继续往下走（建议顺序）

1. **接一台设备**，跑一次 `entry@ohosTest` 的 hypium 套件（`TimelineMath` / `TimelineClock` / `PreviewLayout` 共 6 个 suite），确认离线绿 = 设备绿。
2. 真机上验证四件事：① 切模板时 Surface 不闪黑（不重建）；② T1~T5 五套布局与导出成品逐帧对齐；③ 拖拽松手画面一次到位、不回跳；④ 行程中间有缺失分钟时，分屏两路仍是同一时刻。
3. 只有在真机上确认 T4 裁切侧别确实可感知时，才去动 `cropStartX` —— 并且先用真机确认 `.position` 百分比基准。

> 本报告描述的代码全部已在磁盘上，`entry@default` 与 `entry@ohosTest` 均可编译，离线纯函数测试 70/70 通过。
