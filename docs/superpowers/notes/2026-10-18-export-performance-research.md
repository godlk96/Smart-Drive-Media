# 导出性能与进度调研

日期：初查 2026-10-18，实施 2026-10-19。范围：现有 ArkTS → NAPI → FFmpeg 导出链路。前半部分保留实施前调研，用户批准后的修改和验证见末尾。

## 已确认的开销

| 优先级 | 现状与位置 | 优化方向 | 证据边界 |
| --- | --- | --- | --- |
| 高 | `ExportService.ets` 根据 T5 策略把同一前视轨同时填入 front/back；`ExportNativeService.ets:361` 分别物化；`export_engine.cpp:1880`、`:1888` 分别拼接 | 每次任务内按源 URI 复用正在复制的 Promise 和结果；T5 复用前视拼接结果，避免生成完全不用的后视中间文件 | T5 视频滤镜只使用 frontPath；多文件输入时才会生成拼接文件。节省的是重复输入准备与拼接，不能据此承诺整体耗时减半 |
| 高 | `export_engine.cpp:212`、`:367` 的 movie/amovie 从开头读取，后接 trim/atrim；每个选区创建独立源 | 在选区前使用 seek_point，继续保留精确 trim/atrim 和时间戳归零 | 已验证桌面视频滤镜；应用 FFmpeg 版本、音频及真机仍需验证 |
| 中 | 请求携带模板整条轨道，原生先拼完整轨，再裁选区 | 后续只准备命中选区的源文件，并重映射片段时间 | 跨文件剪辑、源文件真实时长、轨道缺口和多机位对齐需要专门验证，建议另批实施 |
| 中 | `ExportNativeService.ets:238` 和 `ExportManager.ets:333` 每块分配 1 MiB 缓冲区，写入前再 slice | 每个复制任务复用缓冲区，通过写入 length 避免完整块的二次复制；检查实际写入字节数 | SDK 的 fs.write 支持 length，返回 Promise<number>。收益尚未测量，必须处理短写 |
| 低 | 每次导出均调用 `tryWarmupOhosBridge`，额外创建滤镜、解码约 8 帧，然后释放 | 测量后移为诊断检查或复用结果 | 正式编码并不使用这次预热的解码结果，不应将它误认作硬件解码管线 |

现有正式路径已经优先尝试 OHCodec H.264/HEVC 编码器，故“启用硬件编码”不能直接当成新增优化。是否实际回退系统软件编码需要设备日志确认。

## 桌面对照实验

- FFmpeg：仓库本地工具 `ffmpeg version 9.0.2-essentials_build-www.gyan.dev`；不等同于应用链接的 FFmpeg 构建。
- 样本：`media_resource/DVR_LoopRecording_2026-09-11_16-58-56_front_camera.mp4`，174,927,632 字节，HEVC，1920×1080，20 fps。
- 基线滤镜：`movie=源文件,trim=start=40:end=50,setpts=PTS-STARTPTS,fps=20/1,scale=1920:1080,format=pix_fmts=yuv420p,setsar=1`。
- 对照仅增加 `movie` 的 `seek_point=39`；输出为 framemd5，包含解码、滤镜和哈希，不含硬件编码、输入复制和相册保存。
- 顺序 baseline → seek → seek → baseline；耗时分别为 2.245 / 0.712 / 0.713 / 2.179 秒。
- 均值：基线 2.212 秒，对照 0.7125 秒，约 3.10 倍，耗时减少约 67.8%。两者均输出 200 帧，包含时间戳的逐帧 MD5 记录完全一致。
- 另以非整帧起点 40.125 秒、终点 50.125 秒和 `seek_point=39.125` 检查倍速 0.75 / 1 / 1.5 / 2；帧数分别为 267 / 200 / 133 / 100，四组基线与对照记录全部一致，命令退出码均为 0。
- 该结果只证明这个样本上的视频滤镜优化成立，不能外推为整次导出提速 3.10 倍。音频、不同 GOP、非零起始时间戳、多文件拼接和设备环境仍需覆盖。

FFmpeg 官方说明 movie/amovie 支持 seek_point，trim/atrim 不会主动将时间戳归零；实施时应保留现有 setpts/asetpts：<https://ffmpeg.org/ffmpeg-filters.html#movie>。

## 进度不细腻的原因与拟定行为

1. 准备阶段按“完成几个文件”推进 5–20%；单个大文件复制期间没有字节进度。改为累计实际复制字节，无法获知文件大小时退回文件计数，并显示当前素材数量。
2. 原生 20–25% 包含探测、校验、预热及全部轨道拼接，拼接过程中没有进度。为探测与拼接设置明确阶段，拼接按已处理数据或可靠的轨道时间更新。
3. 编码阶段已有 currentFrame/totalFrames，ArkTS 却只读取整数 percent，且 `ExportManager.ets:100` 再次向下取整。可直接由帧数计算小数进度，展示到 0.1%。
4. `Editor.ets:1170` 的环形进度只设置扫描效果。SDK `CommonProgressStyleOptions.enableSmoothEffect` 支持平滑过渡；实际数值仍以真实工作量为准。
5. 相册保存按整数循环补发事件；同一事件循环中的多次通知不会形成均匀动画，读写出错时还会先补到 99%。改为字节进度，每 100–120 ms 合并通知，保留“等待保存位置”“写入相册”“完成”等准确状态。
6. 100% 只在相册写入完成且成功事件确认时显示；阶段转换不得倒退，取消、异常需停止后续通知。未知总量时展示当前阶段，不用计时器编造增长。

拟定首批范围：任务内素材去重、T5 拼接复用、保留精确裁剪的预定位、复制缓冲区复用，以及上述真实分阶段进度。保持画质、分辨率、倍速和静音语义。更换解码架构、直接向相册编码、仅准备选区文件作为后续独立优化。

外部 Review 的判断按实际证据处理：

| 建议/判断 | 结果与理由 |
| --- | --- |
| 没有 seek 导致重复解码 | 采纳视频定位；真实 FFmpeg 8.0 滤镜对照覆盖四档倍速、多段、六种模板及跨文件边界 |
| `--enable-small` / 找不到符号说明没有 NEON | 不采纳：实际 `config.h` 的 `HAVE_NEON`、`HAVE_NEON_EXTERNAL`、`HAVE_NEON_INLINE` 均为 1；库仅保留 `.dynsym`，无 `.symtab`，缺少内部函数名不能证明优化缺失 |
| 滤镜默认单核 | 不采纳该判断：FFmpeg 8.0 movie 未显式设置 `dec_threads` 时使用滤镜线程数，默认自动；本次明确预算，避免多路自动线程争用，不声称从单核升级 |
| 改 `fast_bilinear` | 不采纳：会改变缩放质量，违反本轮保持画质的要求 |
| `fs.copyFile` 零复制 | 不作此承诺：该接口没有进度/取消参数，选用共享可取消复制实现，常规路径只保留一个 1 MiB 缓冲区 |
| 重建 FFmpeg | 本轮不需要：没有证据支持缺少 SIMD；实际硬件编码已在原路径中优先启用 |

音频定位在真实样本上未通过一致性检查：0.75 倍速、1 秒预滚时，输出字节数相同，但 172,364 个浮点样本不同，峰值差 0.0033257287。检查 FFmpeg 8.0 AAC 源码发现 PNS 使用持续 `random_state`；因此撤回音频 seek，保留从头解码和 atrim。音频测试约 0.07 秒，未为这点耗时改变声音。代价是音频读取不享受 seek 加速。

进度改为准备字节 / 检查文件数 / 拼接字节 / 编码帧数 / 封装 / 等待选择保存位置 / 相册写入。保留一位小数，环形启用 `enableSmoothEffect`，非终态通知约每 120 ms 合并，阶段切换即时通知。未知总量时显示当前字节/阶段，不用时间伪造百分比。相册实际写入、fsync、关闭成功后才发 100%；空文件和写入/落盘/关闭错误均拒绝成功。旧任务完全退出后才允许下一次导出；native 在入队前重置状态，排队期间的取消不会被工作线程清除。
