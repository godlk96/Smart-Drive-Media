# 跨段静音 · 方案调研（单轨单播放器路线）

> 背景与根因：见 `docs/预览播放器-声音断续与进度卡顿-根因诊断.md`
> 硬约束（用户明确）：**不要回到多 AVPlayer / PingPong**（更难维护）
> 结论：**不需要第二个播放器** —— HarmonyOS API 26 的 `AVPlayer` 自带**播放列表**，
> 一个 `AVPlayer` 就能把同一机位的多个 60s 切片串起来播放，且官方示例里换段**不调用 `reset()`**。

---

## 一、结论先行

现在每 60 秒一次静音，是因为"换切片"走了官方文档里**唯一被记录的换源方式**：

```
reset() → 回到 idle → 设置 url/fdSrc → prepare() → play()
```

`reset()` 会释放播放引擎（官方文档原话："当播放处于 prepared/playing/paused/completed 状态时，
播放引擎处于工作状态，这需要占用系统大量的运行内存"），所以这段必然是静音 + 无进度。

**API 26 给 `AVPlayer` 加了播放列表**，把"换源"从"应用层拆引擎"变成"播放器内部切条目"：

| | 现在 | 播放列表方案 |
|---|---|---|
| 播放器数量 | 每槽 1 个 | **每槽 1 个（不变）** |
| 换段动作 | `reset()` + `openSync` + `fdSrc` + `prepare()` | `advanceToNextMediaSource()` / `advanceToMediaSource(id)` |
| 是否需要第二个 Surface | 否 | **否（不变）** |
| 与重构反目标 #1 冲突 | — | **不冲突** |

即：**既不是 PingPong，也不需要第二个播放器**，只是把"换文件"交给播放器的列表机制。

## 二、API 事实（全部来自本机 SDK 声明与官方参考文档）

SDK：`C:\Program Files\Huawei\DevEco Studio\sdk\default\openharmony\ets\api\@ohos.multimedia.media.d.ts`
官方参考：`openharmony/docs` → `zh-cn/application-dev/reference/apis-media-kit/arkts-apis-media-AVPlayer.md`

### 2.1 播放列表 API（全部 `@since 26.0.0`，Stage 模型）

| API | 签名 | 说明 |
|---|---|---|
| 建源 | `media.createMediaSourceWithFd(fdSrc: AVFileDescriptor): MediaSource \| undefined` | **本地文件也能作为 MediaSource** |
| 加入 | `addPlaybackMediaSource(src: MediaSource, id?: string): Promise<string>` | 返回唯一 ID；`id` 表示插到该条之前，省略则追加到末尾 |
| 切换 | `advanceToNextMediaSource(): Promise<void>` | 结束当前条目，开始播放下一个 |
| 切换 | `advanceToPrevMediaSource(): Promise<void>` | 上一个 |
| 切换 | `advanceToMediaSource(id: string): Promise<void>` | 跳到指定条目 |
| 移除 | `removePlaybackMediaSource(id: string): Promise<void>` | 从列表移除 |
| 清空 | `clearPlaybackList(): Promise<void>` | 清空列表（当前播放立即终止） |
| 查询 | `getMediaSources(): Array<MediaSource \| undefined>` / `getCurrentMediaSource()` | 列表 / 当前条目 |
| 事件 | `onPlaybackContentChanged(callback: Callback<string>)` | **"播放内容发生变化"时上报正在播放的条目 ID** |
| 循环 | `PlaybackStrategy.playlistLoopMode?: PlaylistLoopMode` | `ALL=1`(默认) / `ONE=2` / `SHUFFLE=3` / **`NONE=4`** |

### 2.2 官方示例的调用顺序（关键）

```ts
let mediaSource1 = media.createMediaSourceWithUrl(...)
await player.addPlaybackMediaSource(mediaSource1)
let mediaSource2 = media.createMediaSourceWithUrl(...)
await player.addPlaybackMediaSource(mediaSource2)

await player.prepare()     // ← 列表加完只 prepare 一次
await player.play()
await player.advanceToNextMediaSource()   // ← 播放中直接切，全程没有 reset()
```

**注意**：`playlistLoopMode` 默认是 `PLAYLIST_LOOP_MODE_ALL`（循环整个列表），
本项目必须显式设为 `PLAYLIST_LOOP_MODE_NONE`，否则整个行程会无限循环。

### 2.3 顺带发现的内置度量（用于验证，API 23）

`player.onMetricsEvent(callback: Callback<Array<AVMetricsEvent>>)` +
`PlaybackMetricsKey`：`PREPARE_DURATION`、`FIRST_FRAME_DECAPSULATION_DURATION`、
`STALLING_COUNT`、`TOTAL_STALLING_TIME`、`LIP_ASYNC_COUNT` 等。
—— **换段代价与卡顿次数可以不用自己打点，直接读播放器的指标。**

### 2.4 版本可用性

`build-profile.json5`：`compatibleSdkVersion: 26.0.0`、`targetSdkVersion: 26.0.0`
→ 播放列表 API 可用，**不需要 `canIUse` 兜底**。
（若将来把最低兼容降到 23，这些 API 需要运行时能力判断。
另注意设计文档里写的"API 23 最低兼容"与 build-profile 的 26.0.0 不一致。）

## 三、映射到现有架构（改造点很小）

`TimelineClock` / `TimelineMath` / `PreviewLayout` / 对账语义**都不用动**，
改动集中在 `SingleTrackController` 一个文件：

| 现在 | 播放列表方案 |
|---|---|
| `beginLoad(uri)`：reset + openSync + fdSrc + prepare | `ensurePlaylistItem(index)`：`createMediaSourceWithFd` + `addPlaybackMediaSource`（每片一个 fd） |
| 靠 `loadedUri` 反查当前段（`getCurrentSegmentIndex`） | 用 `onPlaybackContentChanged(id)` 得到的条目 ID → 段索引 |
| `timeUpdate` → `span.startMs + timeMs` | 不变（`span` 由"当前条目索引"决定，而不是"loadedUri 反查"） |
| 换段 = 对账里发现 `loadedUri !== wantedUri` | 换段 = `advanceToNextMediaSource()`（相邻）或 `advanceToMediaSource(id)`（跨条/跳转） |
| 段末 `completed` → 协调器推进时钟 | 不变；但**相邻且连续时可以让播放器自己接**（列表机制的本意） |

### 3.1 两个必须做的设计决定

**决定 1：列表项按"窗口"懒加载，不要一次性把整趟行程塞进去。**
每个列表项需要一个**独立的 fd**（官方明确警告：同一个 fd 不要交给多个播放器/实例），
20 分钟行程 × 3 机位 = 60 个常开 fd，太浪费。
建议只保留 **前一项 / 当前项 / 后一项**，随着播放推进 `addPlaybackMediaSource` +
`removePlaybackMediaSource` + 关闭 fd。

**决定 2：空洞（该机位缺某一分钟）不能让播放器自动跨过去。**
播放列表的语义是"一条接一条连续播"，它**不知道全局网格里有空洞**：
若把第 1 分钟和第 3 分钟都放进列表，播放器会在第 1 分钟播完后**立刻**播第 3 分钟，
于是这台机位在"第 2 分钟"就已经播到第 3 分钟的内容 —— 破坏"统一视角"。
所以规则是：

- 只有当"当前项之后**紧邻的网格槽位**本机位确实有内容"时，才把下一项加入列表（允许自动接续）；
- 若下一槽是空洞：**不加入下一项**（播放器播完当前项会报 `completed`，画面停在末帧 ——
  与现在的空洞行为一致）；等时钟走到下一个有内容的槽位时，再 `addPlaybackMediaSource` +
  `advanceToMediaSource(id)` + `play()`。

## 四、被否决的方案（以及否决依据）

| 方案 | 否决依据 |
|---|---|
| **恢复 PingPong（每槽 2 个 AVPlayer）** | 用户明确否决；且官方文档警告"按需创建并及时释放，避免持有过多 AVPlayer 实例导致内存消耗过大，否则在一定情况下可能导致系统终止应用"；还要么共享 surfaceId 要么恢复第二个 XComponent，正是本次重构要消掉的东西 |
| **本地 m3u8 / HLS** | 我们的切片是**普通 MP4**（`ftyp free mdat moov`，moov 在尾部），不是 fMP4/TS 分段；HLS 需要 init segment + 媒体分段，容器不匹配，除非先 remux（重编码/重封装成本） |
| **`dataSrc`（AVDataSrcDescriptor）** | 官方明确："如果播放的是 mp4/m4a 格式用户需要保证 moov 字段在 mdat 字段之前，**或者 moov 之前的字段小于 10M**，否则会导致解析失败无法播放"。我们的文件 mdat 是 166MB 且在 moov 之前 → **必然解析失败** |
| **`setMediaSource`** | 官方："流媒体预下载资源设置…**此接口只能在 idle 状态下调用**" → 换源仍要回 idle，等于没解决 |
| **只缩小 reset 开销**（预开 fd、提前 prepare 等） | 省掉的只是零头；`reset()` 释放引擎 + 解码器初始化 + 首帧解码才是主体 |
| **`SEEK_CONTINUOUS`** | 该模式**不上报 `seekDone`**（官方明确），与现有 seek 状态机不兼容；且它解决的是拖动流畅度，不是换段静音 |

## 五、必须在真机确认的清单（本机无设备）

| 编号 | 待确认 | 不确认的后果 | 怎么测 |
|---|---|---|---|
| R1 | **`advanceToNextMediaSource()` / `advanceToMediaSource()` 是否真的无缝**（播放器是否预缓冲下一条） | 若仍是内部 reset，则静音照旧，方案白做 | 用已加的 `★换段静音总时长` 日志；或 `onMetricsEvent` 的 `STALLING_COUNT` / `TOTAL_STALLING_TIME` |
| R2 | `timeUpdate` 在换条后是**从 0 重新计**还是累计 | 时间映射算错 → 进度条跳变 | 日志打印 `timeUpdate` + 当前条目 ID |
| R3 | `onPlaybackContentChanged` 的**触发时机**（在换条后第一个 timeUpdate 之前还是之后） | 短暂用错 `span.startMs` → 播放头跳一下 | 两者都打时间戳 |
| R4 | `addPlaybackMediaSource` / `removePlaybackMediaSource` **能否在 playing 状态下调用** | 不能的话"窗口懒加载"要退化为"一次加满"（fd 压力↑） | 直接试；失败则退化为一次加满 |
| R5 | 列表项的 fd 生命周期（播放器是否一直持有）与**最大可持有 fd 数** | fd 泄漏 / 打开失败 | 观察 `getMediaSources().length` 与 fd 计数 |
| R6 | 自动接续行为：条目播完后**是否自动播下一条**（受 `playlistLoopMode` 影响） | 与"空洞不加入下一项"的规则配合错 → 提前播放下一段 | 只放 2 条、观察是否自动接 |
| R7 | 换条后 `seek()` 的语义（相对当前条目） | 拖动/对账错位 | 换条后 seek 到 5000 看 timeUpdate |

## 六、建议的落地顺序（每步可回退）

1. **先验证 R1**（最小成本、决定方案生死）：
   在 `SingleTrackController` 里加一个**开关**（`USE_PLAYLIST = false` 默认），
   打开后：把当前机位的全部切片用 `createMediaSourceWithFd` + `addPlaybackMediaSource` 加满，
   `playlistLoopMode = NONE`，`prepare()` 一次，播放中在段末调 `advanceToNextMediaSource()`，
   并监听 `onPlaybackContentChanged` 打印条目 ID 与 `timeUpdate`。
   跑一趟真机，看 `★换段静音总时长`：**降到几十毫秒 → 方案成立**；**仍是几百毫秒~1s → 换方案。**
2. R1 成立后，再做"窗口懒加载 + 空洞规则 + fd 回收"的完整版。
3. 全程保留现有单播放器路径作为兜底开关，出问题可一键回退。
4. 最后用 `onMetricsEvent` 的 `STALLING_COUNT` / `TOTAL_STALLING_TIME` 做回归基线。

> 说明：本文所有 API 事实都可复核（SDK 声明 + 官方参考文档）；
> 但"换条是否无缝"属于平台行为，**只能真机验证**，这也是第 1 步要先做的原因。

## 七、R1 探针已经写好（默认关闭）

代码位置：`entry/src/main/ets/media/SingleTrackController.ets`

```ts
const USE_PLAYLIST_PROBE: boolean = false   // ← 改成 true 打开探针
```

**打开后会发生什么**（只影响播放链路，UI/时钟/对账语义都不变）：

1. 每个槽位把自己的全部切片用 `media.createMediaSourceWithFd` + `addPlaybackMediaSource`
   建成播放列表，`playlistLoopMode = PLAYLIST_LOOP_MODE_NONE`，**只 `prepare()` 一次**；
2. 换段不再 `reset()`：优先让播放器自己按列表接续；只有当播放器停在 `completed`
   （说明它没有自动接续）时才调 `advanceToNextMediaSource()`；
3. 监听 `onPlaybackContentChanged`，每次换条打印一行。

**要看的日志**（tag「智驾影音」，或 `tools/sync_full_log.ps1 -PullFromDevice`）：

| 日志 | 说明 |
|---|---|
| `★播放列表换条 id=... span=... 距请求=Xms 距末次上报=Yms` | **Y 就是换条静音时长**（距上一次 timeUpdate 的墙钟间隔） |
| `playlist: 建列表完成 条目=N/M fd=K` | 列表是否建全、fd 数量（同时验证 R5） |
| `playlist: 播放器未自动接续，改用 advanceToNextMediaSource` | 说明**没有**自动接续（R6），走的是应用驱动切换 |
| `playlist: prepared 当前条目 id=... span=...` | R3：初始条目能否正确识别 |
| `★换段静音总时长=...` | 对照组（关闭探针时的 reset 路径静音时长） |

**判据**：`★播放列表换条` 的"距末次上报"降到几十毫秒 → 播放列表方案成立，继续做窗口懒加载 + 空洞规则；
若仍是几百毫秒~1s → 说明播放器内部同样要重建解码链，方案不成立，需要换方向（或接受静音 + 只修进度条）。

**探针阶段的已知取舍**（真机验证通过后再处理，先不要当成 bug）：
- 一次把全部切片加进列表 → 每槽 fd 数 = 该机位切片数（20 分钟行程约 20 个/槽）；
- 空洞未处理（列表会连续播过去），因此探针只用来量换条耗时；
- 非强制跳转（例如空洞结束回到内容段）会继承"载入后先播错位置约 0.7s"的老毛病
  （见根因诊断第七节第 2 条），与 R1 无关。
