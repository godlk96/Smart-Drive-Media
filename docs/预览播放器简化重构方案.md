# 预览页播放器：根因诊断与简化重构方案

> 目标：让"多画面拼接 + 多视频拼接（统一视角延续）+ 拖拽"这三件事由**一套**机制支撑，
> 而不是三套互相打架的状态机。核心是把"事件驱动的状态机"改成**单一时间权威 + 幂等对账器**。

---

## 一、结论先行

现在的播放器不是"有几个 bug"，而是**架构上必然持续产生 bug**。三个具体原因：

1. **同一个"当前播放时间"有 3 个独立写者**，靠 4 层启发式（阈值/epoch/settle 窗口/barrier）互相打补丁。每修一处，就移动了另一处的边界条件 → "修好这个又出那个"。
2. **在事件回调里做异步 IO**（`completed` 里直接换段、`stateChange` 里直接 `reset()+openSync`），绕过了串行队列，于是同一个 `currentSegmentIndex` 有两个写者，只能用 `activeLoadedSegmentIndex` 这种补丁去猜"到底加载的是哪一段"。
3. **用超时掩盖竞态**（1500 / 2000 / 3000ms 三个超时 + 1800ms 模板就绪超时），超时后又继续往下走，于是产生"无 surface 的 prepare"这类非确定性黑屏。

**修复方向不是继续加补丁，而是删掉这套机制。** 目标形态：

```
         ┌──────────────────────────────┐
         │  TimelineClock  (唯一时间权威) │
         │  playheadMs / playing / rate  │
         └──────────────┬───────────────┘
                        │ 订阅（单向）
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   Reconciler(Front) Reconciler(Left) Reconciler(Right)
        │               │               │
   AVPlayer+段列表  AVPlayer+段列表  AVPlayer+段列表
        │
        └─ 主轨 timeUpdate → 回写 clock（唯一的"自动推进"入口）
```

- 每个 Reconciler 是**幂等纯对账**：给定时钟位置，算出"我该播哪一段的哪一毫秒"，只在必要时动 player。
- 幂等 → 重复 seek / 重复换段**天然无害** → 不需要 epoch 丢弃、不需要 seekToken、不需要 settle 窗口、不需要 barrier。
- 并发调用用**"最新值合并"**（latest-wins coalescing）替代队列 + 静默丢弃。

下面先给证据（带行号），再给方案。

## 二、当前架构诊断（含代码位置）

### 2.1 三个独立的时间源

| # | 时间源 | 位置 | 写什么 |
|---|---|---|---|
| 1 | `GlobalTimelineManager.globalPlayheadMs` | `entry\src\main\ets\media\GlobalTimelineManager.ets:12` | 由主轨 `timeUpdate` 写入 |
| 2 | `Editor.state.playheadSec` | `entry\src\main\ets\pages\Editor.ets:61` | 由 `syncGlobalPlayhead()` 写入（`Editor.ets:224-240`） |
| 3 | 各轨自己的 `segment.startMs + playerTime` | `entry\src\main\ets\media\SingleTrackController.ets:637-651` | 每条轨各自换算全局时间 |

`Editor.ets:224-240` 的 `syncGlobalPlayhead(second, fromUser, commitSeek)` 还额外接受 `fromUser` / `commitSeek` 两个标志来决定"要不要真的 seek"——**同一件事（跳到某时间）有两条入口**。

### 2.2 四层启发式过滤，层层叠加

```
主轨 timeUpdate
  → [第1层] GlobalTimelineManager.ets:73   if (this.isSeeking || this.isBarrierSwitching) return
  → [第2层] GlobalTimelineManager.ets:151  if (currentEpoch === this.seekEpoch) { ...只在这里采纳... }
  → [第3层] Editor.ets:477                 if (!this.previewPlaying || this.isTimelineDragging) return
  → [第4层] Editor.ets:481-488             if (Math.abs(nextSec - this.settleTargetSec) < 0.55) return   // 拖动后 260ms 内的回调全丢
```

`Editor.ets:41-43` 是 `settleTargetSec / settleTimer / settleWindowMs = 260`，`Editor.ets:535-541` 在拖动中起定时器。这四层都是"猜这一帧是不是过期的"。**任何一层改了，另外三层的假设就失效** —— 这正是"修一个出另一个"的机制。

更糟的是：`GlobalTimelineManager.ets:68-91` 里 `registerTrack` 的进度回调**只在 `playbackState === 'playing'` 时采纳**。所以暂停时播放头完全不动；seek 后的新位置必须靠 `seek()` 内部手动补发 `onPlayheadChanged`（`GlobalTimelineManager.ets:151-157`）。**UI 的播放头位置有两个来源**，暂停/播放切换时必然出现回跳或不动。

### 2.3 事件回调里做异步 IO → 双写者竞态

`SingleTrackController.bindPlayerEvents()`（`SingleTrackController.ets:506`）里：

- `stateChange === 'completed'` 分支（`:590-615`）**直接调用 `loadSourceInternal(nextSeg.uri, 0)`** 并改 `currentSegmentIndex` —— 这条路**不在 `enqueue` 串行队列里**。
- 而 `seekTo()`（`:221-232`）、`switchSegment()`（`:234-257`）在队列里也改同一个 `currentSegmentIndex`。

两个写者 → 于是需要 `activeLoadedSegmentIndex`（`:30`，在 `:409` 被赋值、在 `:591` 被比较）来猜"实际加载的是哪一段"。**这个字段的存在本身就是竞态的证据。**

同时，`GlobalTimelineManager.performBarrierSwitch()`（`:196-211`）对**所有**轨（含主轨）调 `seekTo(segEnd)`，而主轨自己的 `completed` 也可能触发换段 → **同一段被加载两次**（双 `reset()` + 双 `openSync`）。

### 2.4 单槽 Promise 字段 → 等待者互相覆盖

`SingleTrackController.ets:45-47`：

```ts
private preparedResolve?: () => void
private pendingSeekResolve?: () => void
private surfaceResolve?: () => void
```

都是**单槽**。两个并发等待（例如 `seekTo` 和 `completed` 同时触发）时，后者覆盖前者，前者的 Promise 只能等超时。对应的三个超时：

- `waitForSurface(timeoutMs = 1500)` — `SingleTrackController.ets:153-167`
- `seekPlayer()` 内 2000ms — `SingleTrackController.ets:477-504`
- `waitPrepared()` 内 3000ms — `SingleTrackController.ets:454-475`

**这三个超时值是"掩盖竞态"的补丁。** 而且 `waitForSurface` 超时后**仍然继续** `fdSrc` + `prepare()`（`:408-452`），无 surface 的 prepare 可能永不 prepared → 又落进 3s 超时 → 黑屏。

### 2.5 队列"静默丢弃" → 调用方无法区分"完成"和"放弃"

`SingleTrackController.enqueue()`（`:307-313`）里，每个操作开头都有一句：

```ts
if (this.disposed || epoch !== this.lifecycleEpoch) return   // :190, :209, :227, :237
```

**静默 return 让 `await` 正常完成，但操作根本没执行。** 如果 `switchSegment` 被丢弃，该轨就永远不播 → 黑屏，而且**没有任何日志或错误**。这类 bug 在真机上表现为"偶尔某个画面不亮"，无法复现、无法定位。

### 2.6 模板切换 = 跨两个文件的定时器状态机

`Editor.ets:30-37` 有 8 个字段：

```
templateSwitchEpoch / templateSwitchPendingCard / templateSwitchLoopRunning
templateSwitchWaitVersion / templateSwitchReadyVersion / templateSwitchReadyResolver
templateSwitchReadyTimeoutMs = 1800 / templateSwitchLoadingMinMs = 160
```

配合 `EditorPreviewArea` 的 `applyEpoch / lastAppliedKey / applyQueue / onRebuildReady / renderVersion / switchTaskId`（`Editor.ets:47,49`，`EditorPreviewArea.ets` 内）。**跨文件 8+ 个字段、2 个超时的握手协议**，本身就是竞态源；而且 `Editor.ets:708` 和 `:646` 各有一处 `seekToken += 1`，与这套版本号并行。

### 2.7 布局定义重复且**互相矛盾**

- `entry\src\main\ets\model\Models.ets:165-168`（T4）：`0.3333 / 0.3334 / 0.3333`，**无 zoom**
- `entry\src\main\ets\components\EditorPreviewArea.ets:169-171`（T4）：`0.25 / 0.50 / 0.25`，且 `zoomX: 2.0`

同一个模板，预览和导出用**两套不同的几何定义**。`resolveLayout()`（`EditorPreviewArea.ets:147-176`）整体重复了 `TEMPLATE_DEFINITION_MAP[].previewSlots`，两者已经开始漂移。→ "预览所见 ≠ 导出所得"是**结构上**的，不是偶发 bug。

### 2.8 分段模型的"索引空间"与"时长"用了两套语义（已核实的真 bug）

三处代码各自成立，组合起来矛盾：

| 位置 | 代码 | 语义 |
|---|---|---|
| `EditorPreviewArea.ets:263` | `const startMs = sliceIndex * 60000` | **索引空间**：按唯一切片时间戳排序后的序号 |
| `CoreBridge.ets:403` | `durationSec = Math.max(60, round((endTs - startTs) / 1000))` | **墙钟跨度**：首片到末片末尾的真实秒数 |
| `CoreBridge.ets:464` | `merged.durationSec = selected.reduce((a, i) => a + i.durationSec, 0)` | **求和**：各行程时长相加 |

- 合并行程里 `uniqueTimestamps` 是连续的（空隙不贡献索引），而 `durationSec` 是求和 → **两者恰好一致**，所以合并行程反而是对的。
- **单行程里两者会不一致**：`TRIP_GAP_THRESHOLD_MS = 120 * 1000`（`CoreBridge.ets:30`）配合 `:372` 的 `sliceEndTs = ts + 60000` 与 `:377` 的 `ts - lastSliceEndTs <= TRIP_GAP_THRESHOLD_MS`，意味着**行程内缺 1～2 分钟仍会被归为同一行程**。此时：
  - `durationSec` 按墙钟算 → 多算 60～120s
  - 索引空间按实际切片数算 → 少 1～2 个索引
  - → **时间轴尾部有 60～120s 没有任何 segment**

后果链路（逐行可查）：
`resolveSegment()`（`SingleTrackController.ets:342-361`）的 for 循环找不到容纳 `clamped` 的段 → 走到 `:360` 的 `return { segmentIndex: 0, offsetMs: 0 }` → `seekInternal` 在 `:389-391` 执行 `currentSegmentIndex = 0` 并 `loadSourceInternal(segment0.uri, 0)` → **该轨跳回行程开头**。

`resolveSegment` 的兜底（`:352-360`）还把"超过末尾"（`:357-359`，返回最后一段）和"落在空洞/开头之前"（`:360`，返回第 0 段）两种语义压在同一处，这是它难以察觉的原因。

> 附带发现：`EditorPreviewArea.ets:187` 的 `getSnapshotBaseTimestamp(snapshot)` 定义了**但全项目没有任何调用点**（grep 只命中定义处）。它是"按墙钟锚点计算 startMs"的正确思路的残留，说明之前有人试过又放弃了。

### 2.9 隐藏槽位的 Surface 生命周期不确定

`EditorPreviewArea.ets:487` 用 `.visibility(item.visible ? Visibility.Visible : Visibility.Hidden)` 隐藏多余槽位；而 `SingleTrackView.onLoad`（`entry\src\main\ets\components\SingleTrackView.ets:17-25`）**只在挂载时上报一次** surfaceId。

模板从 2 槽切到 3 槽时，若隐藏槽的 Surface 已被系统回收，controller 仍持有旧 surfaceId → 黑屏。这是"点击无画面"的**非确定性**来源，需真机确认，但按现有写法风险确实存在。

## 三、目标架构

三条原则：

1. **单一时间权威**：全局只有一个 `playheadMs`，UI 只是它的订阅者。
2. **幂等对账替代状态机**：给定时钟位置，每轨独立算出该做什么；重复执行无副作用。
3. **事件只做通知，不做决策**：`prepared` / `completed` / `error` 只更新本轨的"可用状态"，换段决策统一由对账器做。

### 3.1 TimelineClock —— 唯一时间源

新建 `entry\src\main\ets\media\TimelineClock.ets`：

```ts
export class ClockSnapshot {
  playheadMs: number = 0
  durationMs: number = 0
  playing: boolean = false
  rate: number = 1
  dragging: boolean = false
}

export class TimelineClock {
  private playheadMs: number = 0
  private durationMs: number = 0
  private playing: boolean = false
  private rate: number = 1
  private dragging: boolean = false
  private dragPreviewMs: number = 0
  private listeners: Array<(s: ClockSnapshot) => void> = []

  /** UI 唯一读入口：拖动时显示 preview，否则显示真实值 */
  getVisibleMs(): number {
    return this.dragging ? this.dragPreviewMs : this.playheadMs
  }

  getSnapshot(): ClockSnapshot { /* 组装 */ }

  subscribe(fn: (s: ClockSnapshot) => void): () => void { /* 返回取消函数 */ }

  setDuration(ms: number): void {
    this.durationMs = Math.max(0, ms)
    this.playheadMs = Math.min(this.playheadMs, this.durationMs)
    this.emit()
  }

  /** 唯一的跳转入口。拖动松手、点击进度条、切片段、切模板全走这里。 */
  seek(ms: number): void {
    this.playheadMs = this.clamp(ms)
    this.dragging = false
    this.emit()
  }

  /** 拖拽中：只改 UI 预览值，绝不动任何 player */
  setDragPreview(ms: number): void {
    this.dragging = true
    this.dragPreviewMs = this.clamp(ms)
    this.emit()
  }

  /** 唯一的"自动推进"入口：只有主轨的 timeUpdate 调它 */
  advanceFromMaster(globalMs: number): void {
    if (!this.playing || this.dragging) return
    const next = this.clamp(globalMs)
    if (next === this.playheadMs) return
    this.playheadMs = next
    this.emit()
  }

  setPlaying(playing: boolean): void {
    if (this.playing === playing) return
    this.playing = playing
    this.emit()
  }

  private clamp(ms: number): number {
    if (ms < 0) return 0
    if (ms > this.durationMs) return this.durationMs
    return ms
  }

  private emit(): void {
    const snap = this.getSnapshot()
    this.listeners.forEach((fn) => fn(snap))
  }
}
```

要点：
- **删除** `seekToken` / `seekBlocked` / `settleTargetSec` / `settleTimer` / `settleWindowMs` / `isTimelineDragging` / 0.55s 阈值 —— 全部不再需要。
- 拖拽期间播放头由 `dragPreviewMs` 提供，**松手一次 `seek()`**，不存在"被旧回调拽回去"。
- `advanceFromMaster` 不再需要 epoch 门禁：主轨在 seek 期间由下面的 `suppressProgress` 屏蔽上报。

### 3.2 TrackReconciler —— 幂等对账

改造 `SingleTrackController`，核心从"命令式方法 + epoch 丢弃"变成"对账"：

```ts
export class Desired {
  globalMs: number = 0
  playing: boolean = false
  rate: number = 1
}

// ---- 段模型：累积时长，无空洞 ----
export class SegmentSpan {
  uri: string = ''
  startMs: number = 0      // 相对行程起点的累积值
  durationMs: number = 0
}

/** 纯函数：全局时间 → 该轨的段内目标。segments 恰好铺满 [0, totalMs)，无空洞。 */
function segmentAt(segments: Array<SegmentSpan>, globalMs: number): SegmentTarget | undefined {
  if (segments.length === 0) return undefined
  let acc = 0
  for (let i = 0; i < segments.length; i++) {
    const seg = segments[i]
    if (globalMs < acc + seg.durationMs) {
      return { index: i, offsetMs: Math.max(0, globalMs - acc), segmentStartMs: acc }
    }
    acc += seg.durationMs
  }
  return undefined          // 超过本轨末尾 → 明确返回 undefined，不再"跳回第 0 段"
}
```

对账主体（**latest-wins 合并，替代队列 + epoch 丢弃**）：

```ts
private applying: boolean = false
private pendingDesired?: Desired

async reconcile(d: Desired): Promise<void> {
  this.pendingDesired = d
  if (this.applying) return            // 正在跑，最新的值已经记下，跑完会再跑一次
  this.applying = true
  try {
    while (this.pendingDesired) {
      const cur = this.pendingDesired
      this.pendingDesired = undefined
      await this.applyOnce(cur)
    }
  } finally {
    this.applying = false
  }
}

private async applyOnce(d: Desired): Promise<void> {
  if (this.disposed) return

  // 1) 对齐播放态
  if (d.playing !== this.isPlayingNow) {
    await this.setPlayingInternal(d.playing)
  }
  // 2) 对齐速率
  if (d.rate !== this.currentRate) {
    await this.setRateInternal(d.rate)
  }

  // 3) 对齐画面位置（这里才动 player）
  const target = segmentAt(this.segments, d.globalMs)
  if (!target) {
    // 本轨已到末尾：停在最后一帧，明确处理，不跳回开头
    if (this.isPlayingNow) await this.setPlayingInternal(false)
    return
  }

  if (target.index !== this.loadedIndex) {
    await this.openSegment(target.index, target.offsetMs)   // reset + fdSrc + prepare + seek
    this.loadedIndex = target.index
    return
  }

  // 同段内：只有偏差超过阈值才 seek，避免每帧都 seek
  const drift = Math.abs(this.currentPlayerTimeMs - target.offsetMs)
  if (drift > 300) {
    await this.seekPlayer(target.offsetMs)
  }
}
```

**为什么这就够了**：`reconcile` 是幂等的 —— 同一个 `Desired` 调 100 次，只有第一次会真的 `openSegment`。所以：
- 不需要 `lifecycleEpoch` / `seekEpoch` 去"丢弃过期操作"；
- 不需要 `queue` 去"串行化"（`applying` 标志已经保证同时只有一个 `applyOnce`）；
- 不需要 `waitForSurface` / `waitPrepared` / `seekPlayer` 的**超时**（下面讲正确的等待方式）；
- 不需要 `activeLoadedSegmentIndex`（`loadedIndex` 只在 `applyOnce` 里被写，单写者）。

`suppressProgress`（替代 seek 期间的 epoch 门禁）：

```ts
private suppressProgress: boolean = false

private async seekPlayer(offsetMs: number): Promise<void> {
  if (!this.player) return
  this.suppressProgress = true
  try {
    await this.player.seek(offsetMs, media.SeekMode.SEEK_CLOSEST)
  } finally {
    this.suppressProgress = false
  }
}
// timeUpdate 回调第一行：
if (this.suppressProgress) return
```

### 3.3 段边界：让时钟"连续"，删掉 barrier

现在的 barrier（`GlobalTimelineManager.ets:182-211`，`checkMasterBarrierSegment` + `performBarrierSwitch` + `isBarrierSwitching`）是为了"在段切换时把所有轨对齐"。新方案里**不需要它**，因为：

- 段列表用**累积时长**构造 → `segments[i].startMs === segments[i-1].startMs + segments[i-1].durationMs`，段与段**严格连续**。
- 主轨的 `completed` 事件只做一件事：把时钟推到边界。

```ts
// 主轨 completed 回调（唯一用途）
const boundaryMs = this.currentSegmentStartMs + this.currentSegmentDurationMs
this.onMasterProgress(boundaryMs)      // 即 clock.advanceFromMaster(boundaryMs)
```

时钟到边界 → 所有 Reconciler 收到新 `Desired` → 各自换段。主轨换段后 `timeUpdate` 从 0 开始，映射回来正好是 `boundaryMs`：

```
globalMs = 新段.startMs + playerTime = boundaryMs + t     // 严格连续，不跳变
```

于是**不需要** `isBarrierSwitching`、`pendingSeekMs`、`seekEpoch`、`seekRequestGate`、`trackEndedFlags`、`endedEmitted`（`GlobalTimelineManager.ets:14-19, 9-10`）。

各轨异步换段的几十毫秒空档是 `AVPlayer` 逐文件播放的固有代价，人眼无感；不再用 barrier 去"藏"它 —— 藏的过程才是 bug 源。

### 3.4 多视频拼接（统一视角延续）

一个机位 = 一条逻辑轨 = 一个 `AVPlayer` + 一个 `SegmentSpan` 列表。

**关键约束：所有机位必须共享同一个时间网格，否则多画面会失去同步。**

反例（我第一版方案里的错误）：如果按"各机位自己的累积时长"排布 segment，那么机位 A 缺了第 3 分钟、机位 B 缺了第 7 分钟时，两者的累积时长不同 → 全局时间 150s 处 A 显示第 4 分钟、B 显示第 5 分钟 → **多画面展示的不是同一时刻**，直接违背"统一视角"。

正确做法：**索引网格**。所有机位共用同一套 `uniqueTimestamps`（取自 `snapshot.clips`，`EditorPreviewArea.ets:252-254`），`startMs = sliceIndex * 60000` 保持不变。某机位缺切片时，它自己的 segment 序列出现空洞 —— 这是**该机位的事实**，不是模型的错误。

需要两处修复：

**修复 1（时长语义统一）**：`CoreBridge.ets:403` 改为按唯一切片数计算，让单行程与合并行程语义一致：

```ts
// 旧：墙钟跨度 —— 行程内缺分钟时会多算，导致时间轴尾部无 segment
// durationSec = Math.max(CLIP_DURATION_SEC, Math.round((endTs - startTs) / 1000))
// 新：与 buildTrackSegments 的索引空间一致
const uniqueSliceCount = new Set(allClips.map((c) => c.timestamp)).size
const durationSec = Math.max(CLIP_DURATION_SEC, uniqueSliceCount * CLIP_DURATION_SEC)
```

这样 segment 恰好铺满 `[0, durationMs)`，"尾部无段"的问题消失。

**修复 2（空洞显式化）**：`segmentAt` 对空洞返回明确的"无内容"状态，而不是掉进"跳回第 0 段"的兜底：

```ts
export class SegmentTarget {
  kind: 'content' | 'gap' = 'content'   // gap = 本机位此处确实没有素材
  index: number = -1
  offsetMs: number = 0
}

/** 纯函数：全局时间 → 目标。无任何副作用，可离线单测。 */
function segmentAt(segments: Array<SegmentSpan>, globalMs: number): SegmentTarget {
  for (let i = 0; i < segments.length; i++) {
    const s = segments[i]
    if (globalMs >= s.startMs && globalMs < s.startMs + s.durationMs) {
      return { kind: 'content', index: i, offsetMs: globalMs - s.startMs }
    }
    if (globalMs < s.startMs) {
      // 落在本段之前 → 处于空洞中（或全局起点之前）
      return { kind: 'gap', index: i, offsetMs: 0 }
    }
  }
  // 超过末尾：停在最后一帧，不跳回开头
  return { kind: 'gap', index: segments.length, offsetMs: 0 }
}
```

`gap` 的处理策略由产品决定，但**必须是显式的**：
- 保持上一帧（`pause()` 但不清屏）—— 推荐，最不干扰
- 或显示黑场 + "该视角无素材"提示

无论选哪个，都不再出现"seek 到空洞 → 跳回行程开头"。

**删除**：`templateSwitchEpoch` / `templateSwitchPendingCard` / `templateSwitchLoopRunning` / `templateSwitchWaitVersion` / `templateSwitchReadyVersion` / `templateSwitchReadyResolver` / `templateSwitchReadyTimeoutMs` / `templateSwitchLoadingMinMs`（`Editor.ets:30-37`），以及 `EditorPreviewArea` 的 `applyEpoch` / `lastAppliedKey` / `applyQueue` / `onRebuildReady` / `renderVersion`。

**需要澄清的一点（我第一版说法过强）**：模板切换**并非完全不影响播放器**。
`applyTemplateAndTrip`（`EditorPreviewArea.ets:335-352`）里槽位按索引固定（`for (let i = 0; i < 3; i++)`），但 `slot.camera = camera`（`:345`）会被重新赋值 —— T2 的 slot0 是 `Front`，切到 T4 后 slot0 变成 `LeftFront`。`buildTrackSegments(this.tripSnapshot, camera)`（`:343`）因此返回**不同机位**的 segments，该槽的 controller 必须换媒体源。

所以准确的表述是：

| 层面 | 模板切换是否影响 |
|---|---|
| 组件树结构（XComponent 节点） | **不影响** —— 3 个槽位常驻，这点现有代码已经做对了 |
| 槽位几何（x/y/w/h/zoom） | 只改属性，不影响播放 |
| **槽位↔机位映射** | **会变**，映射变了的槽必须重新加载媒体 → 一次短暂黑闪 |

要彻底做到"切换不碰播放器"，只有让 XComponent **按机位常驻**（在一个 Stack 里渲染全部机位、模板只改各自的 position/size/visibility，不重新挂载）。代价是同时存活的解码器数量上升到机位数（4～6 路），在手机上可能触碰硬件解码上限。

**工程结论**：模板切换是用户主动操作，一次 200ms 黑闪可接受；不值得为它引入 4～6 路常驻解码器。因此**保留"切换时该槽重载媒体"**，只是把握手从 8 字段状态机降为一个 `await`。

## 七、为什么这样就不会"一个接一个"

| 旧机制 | 为什么持续产生 bug | 新机制 |
|---|---|---|
| 3 个时间源 + 4 层过滤 | 每层都在猜"这帧是不是过期"，改一层就破坏其余三层的假设 | 1 个 clock，拖动期用 `dragPreviewMs` 显式区分 |
| epoch 丢弃 | 静默丢弃无法与"完成"区分 → 黑屏无日志 | 幂等对账，重复调用无害，无需丢弃 |
| 串行队列 | 事件回调绕过队列 → 双写者 | `applying` 标志保证单写者，latest-wins 不丢工作 |
| 超时等待 | 超时后继续走 → 非确定性失败 | `await` 真实的 player 状态转换（`prepared` / `seekDone`） |
| barrier 对齐 | 换段路径有两条（barrier + completed） | 换段只有一条路径（reconciler） |
| 模板切换握手 | 跨文件 8 字段 + 2 超时 | 一个 `await`，且不触碰 player |
| 布局定义重复 | 两处定义漂移 → 预览≠导出 | 单一来源 `TEMPLATE_DEFINITION_MAP` |

一句话：**旧的每修一个 bug 都在增加状态；新的每改一个需求只需要改一个纯函数。**

### 8.2 我在这份方案里**自己发现并已修正**的三个错误

诚实记录，因为这说明"读代码得出的方案"也会错：

1. ~~"段列表改成累积时长"~~ → **错**。会让不同机位因缺失分钟不同而失去时间同步，直接违背"统一视角"。已改为保持索引网格 + 空洞显式化（3.4）。

### 8.4 唯一能真正"确保"的部分

**纯函数可以离线测试，这是唯一谈得上确保的东西。**
`segmentAt()`、`durationSec` 计算、`TemplateDefinition` 几何 —— 这些都是纯函数，可以用真实 DVR 元数据写成单元测试（`entry/src/ohosTest/` 已有测试基建），**不需要设备**。8.2 里那三个错误，如果当时有 `segmentAt` 的单测，第 1 个会被立刻发现。

因此推荐的推进顺序是：**先把纯函数和它们的测试立起来，再动播放器**。这样"读代码得出的结论"会被测试检验，而不是靠我又读一遍。

### 8.5 我能给出的最强保证

不是"不出问题"，而是：

- 独立机制数量从 ~15 个降到 ~4 个（clock / reconciler / segmentAt / 几何定义）→ **出错的地方更少**
- 关键逻辑变成纯函数 → **可以被测试**，而不是只能靠真机试
- 删除静默丢弃 → 失败**变响**（这是现有代码最毒的性质：丢弃和完成无法区分）
- 5 步增量 + 每步可回滚 → 出错时**损失有界**

反过来说：如果你要的是"一次改完保证没问题"，那这个方案给不了，任何方案都给不了。它给的是"**错误会更容易被发现、被定位、被回退**"。
