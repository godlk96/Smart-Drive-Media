## 结论（2026-10-13 真机日志确认）

**根因是"合并行程的时间轴跨天"，属于纯数据/模型 bug，与播放器架构无关。已修复。**

用户合并了 3 趟相隔几天的行程（`trip-merged-2026-09-11-165856-3`，`时长=180s`）。旧的
`buildTimeGrid()` 拿**全部切片的墙钟 min/max** 建时间轴，于是 3 分钟的合并行程得到
**190 小时**的时间轴（真机日志：`applied template=T2 slots=3 durationMs=684840000`）。
播放时：

- 第 1 段（60s）播完后，时钟在 60s 处发现"没有任何轨覆盖" → **`skip` 到下一段起点
  68,580,000ms（19 小时）** → 三轨全部 `reset()+prepare()` → 出声轨静音 **366ms** → **声音断断续续**；
- 与此同时 UI 的总时长是**各段之和**（180s），而播放头来自时钟（68,580s）→ 被钳到 100%
  → **进度条跳到末尾并卡住** → **进度条卡顿**。

**修复**（`entry/src/main/ets/media/TimelineMath.ets`）：网格改为**由若干"连续录制段"依次拼接**，
段内仍是墙钟索引网格。**离线纯函数测试 82/82 通过**（含 4 条新增回归用例）。

### 1.6 第六份（11:13:59~11:14:21）：探针第一次真正跑起来 → **把预览跑死了**

`构建标记 版本=probe1-2026-10-13 探针=ON 打点=ON` 出现了 → 新包确认。随后：

```
11:14:02.318~02.327  slot_0/1/2 state -> initialized
11:14:02.333  slot_0/1/2 playlist: 建列表完成 条目=3/3 fd=3        ← 播放列表建成功
11:14:02.333  slot_0/1/2 playlist: 策略已设 playlistLoopMode=NONE
11:14:02.333  slot_0/1/2 playlist: advanceToMediaSource 失败
              BusinessError: current state is not prepared, unsupport AdvanceToMediaSource
11:14:02.343  slot_0/1/2 seek(0) reason=playlist-force drift=0ms
11:14:02.344  slot_0 player error: Operate Not Permit: The current state is initialized,
              seek operation only support prepared/playing/paused/completed state.
11:14:02.343~02.352  slot_1/slot_2 state -> error
              slot_1/slot_2 player error: Unsupported Format: ... hevc-
11:14:02.347  slot_2 ★播放列表换条 id=... span=0 距请求=4ms 距末次上报=-1ms
11:14:02.348  slot_1 ★播放列表换条 id=... span=0 距请求=5ms 距末次上报=-1ms
11:14:02.358  slot_0 state -> prepared
11:14:02.359  slot_0 playlist: prepared 当前条目 id=... span=0
11:14:03.219  【剪辑诊断】点击播放预览，已同步播放全部画面
              ……此后没有任何 slot_* play() / 上报节奏 / ★换段静音 —— 用户报告"完全卡死"
```

**根因（死锁链条，三步）：**

1. `ensurePlaylist()` 末尾刚 `prepare()`（状态还是 `initialized`），`applyDesiredViaPlaylist()`
   紧接着就 `advanceToMediaSource()` → 被拒（"not prepared"）；
2. 同一轮继续走到偏差检查，`forceSeek=true`（模板应用后的首轮对账）→ 直接 `seek(0)`；
   此时状态是 `initialized` → **被拒**（"Operate Not Permit"）；
3. seek 被拒 ⇒ `seekDone` **永远不会触发** ⇒ `seekInFlight` 永久为 `true`；
   而所有对账入口都在 `if (this.seekInFlight && !forceSeek) return` 处返回
   ⇒ `syncPlayState()` 永远走不到 ⇒ **不调 `play()`** ⇒ 主轨 `slot_0` 不产生 `timeUpdate`
   ⇒ 时钟不推进 ⇒ **"完全卡死、没有任何播放进度"**。

`slot_1/slot_2` 因为竞态被打进 `error`（hevc 报错），`slot_0` 侥幸 `prepared` 成功，
但已被第 3 步锁死 —— 所以三轨全不动。这正是 7.7。

**同时这一份也证明了方案本身是通的**（这些是真正的正面证据）：

- 播放列表**建得起来**：`条目=3/3 fd=3`（三个条目、三个独立 fd，全部成功）；
- `onPlaybackContentChanged` **会触发**，且携带的 id **能反查到 spans 下标**
  （`span=0` 说明 `playlistIds.indexOf(id) >= 0`）→ "条目 id → 全局时间"的映射可用；
- `prepared` 后 `getCurrentMediaSource().getID()` 也能反查到（`span=0`）；
- `playlistLoopMode=NONE` 设置成功（不会整趟循环）。

→ **崩的原因是缺一个状态守卫，不是播放列表 API 不可用。** 已按此修复（见第三节）。

### 1.7 第七份（11:19:18~11:21:30）：探针修复后跑通 → **换条快 5 倍，但解复用器起不来**

`构建标记 版本=probe2-2026-10-13 探针=ON`；**6 项修复全部生效**（不再有
`advanceToMediaSource 失败`、不再死锁、三轨正常播放到 120s、`漂移seek=0`）。
**决定性一行：**

```
11:20:21.717 slot_0 ★播放列表换条 id=97135-... span=1 距请求=-1ms 距末次上报=61ms
```

- `距请求=-1ms` → **没有发过 advance 请求** → 是**播放器自己接续**的；
- `距末次上报=61ms` → 从上一个 `timeUpdate` 到换条通知只隔 **61ms**。

| 路径 | 段交界耗时 |
|---|---|
| reset + prepare（第四/五份日志，出声轨，4 个交界） | **322 / 323 / 340 / 377ms** |
| 播放列表自动接续（第七份日志） | **61ms** |

→ **"播放列表能免掉重建解码链"这个判断成立，快约 5 倍。**

**但这一版实现不可用** —— 同一次会话里播放列表路径触发 3 次
`Unsupported Format: DEM_FMT_ERR-unsupport interface, unsupport container format type, hevc-`：

```
启动（三轨同时建表 + prepare）：
11:19:20.720 slot_0 建列表完成 条目=3/3 fd=3   ← 第 1 个 prepare
11:19:20.749 slot_0 state -> prepared                                    OK
11:19:20.720 slot_1 建列表完成 条目=3/3 fd=3   ← 第 2 个
11:19:20.730 slot_1 state -> error   player error: ... hevc-            ✗
11:19:20.720 slot_2 建列表完成 条目=3/3 fd=3   ← 第 3 个
11:19:20.730 slot_2 state -> error   player error: ... hevc-            ✗

交界 1（此时只有 slot_0 还在用播放列表，slot_1/slot_2 已退回 reset 路径）：
11:20:21.717 slot_0 ★播放列表换条 span=1 距末次上报=61ms   ← 换条成功
11:20:21.724 slot_0 state -> error   player error: ... hevc-            ✗
```

- 错误在 `prepare()` 之后 **~10ms** 就出现 —— 对一个 167MB 非 faststart 文件来说**远快于真实解复用**，
  所以这不是"慢/超时"，而是**播放器直接拒绝了这个列表配置**；
- 失败顺序与建表顺序一致（第 1 个成功、第 2/3 个失败），交界处"唯一还在用播放列表"的 slot_0
  在 **advance 时**也失败 → 说明失败点在**播放列表路径本身**，而不是探针的调用时机；
- **同一会话里 reset 路径 0 次**（退回后 slot_0/1/2 一路播到 120s，两次交界都干净）。

**决策：不采用播放列表方案，开关关回 `false`，线上保持已验证的 reset 路径。**
理由：收益（只在多分钟/合并行程的段交界处，把 320~377ms 降到 61ms）**换不来**
"解复用器起不来"的风险；而单趟 1 分钟行程（20 趟里的 16 趟）本来就没有段交界。
探针代码保留（含状态守卫与失败回落），平台日后修复可重新验证。

**这一份同时确认了两件好事**：7.7 的修复有效（不再死锁），
以及 7.7-C 的看门狗与 7.7-D 的兜底回落都在真实故障中正确工作
（`playlist: 播放器进入 error，退回 reset 路径` ×3，每次都自愈并继续播）。


## 二、已实施的修复（5.1）

**问题**：`buildTimeGrid()` 用全部切片的墙钟 min/max 建一条轴，跨天合并时把时间轴拉成几天长。

**修复**：网格改为**由若干"连续录制段"依次拼接**：

- 按 `RUN_GAP_MS`（120s）把切片时间戳切成若干段——该常量与 `CoreBridge.TRIP_GAP_THRESHOLD_MS`
  **同源**（现在由 `CoreBridge` 直接 `import { RUN_GAP_MS, SLICE_MS }`，不会再漂移）；
- 每段内部仍是**墙钟索引网格**（缺的分钟照样占位）→ **"统一视角延续"不变**；
- 各段首尾相接：第 N 段的 `baseSlot` = 前面各段槽位数之和；
- `gridIndexAt()` 改为"先定位所属段、再加 baseSlot"，落在段与段之间返回 -1。

结果：3 分钟的合并行程 = **180 秒、3 个相邻槽位**（不再是 190 小时）。

**验证（离线纯函数，本机可跑）**：

```
离线纯函数测试：82/82 通过          ← 78 条既有 + 4 条新增回归用例
```

新增用例覆盖：
① 合并跨天行程 → 2 段/2 槽位/120 秒，且**段交界处是 content**（旧实现是 gap）；
② 段内 ≤120s 的空洞**仍然保留**（不会被拼接抹掉）；
③ 间隔正好 120s 算同一段、121s 才断开；
④ 落在两段之间的时间戳返回 -1。

`tools/check-grid.mjs` 复算同一对时间戳：`sliceCount=2 durationMs=120000`、
`span[1].startMs=60000`、`segmentAt(60000)=content`（修复前是 `gap`）。

## 三、仍然存在：换源本身要 ~330ms（5.2）

即使时间轴修好，**"换一段素材"这件事本身**仍要 `reset() + openSync + fdSrc + prepare()`：

- 真机实测（第四/五份日志，出声轨 slot_0，共 4 个交界）：**322 / 323 / 340 / 377ms**
  = prepare 216~272ms + `play()` 之后 ~105ms 才出首帧；
- 单趟**多分钟行程**每分钟一次；合并行程在每段交界处一次；
- 三轨同时 prepare 时出声轨最慢（272ms vs 181/185ms）→ 换源瞬间存在解码竞争；
- 静默轨（无音轨）也要 290~320ms，说明这段耗时与"有没有音频"无关，是**重建解码链**本身。

### 为什么旧版没有这个问题

| | 旧实现 `PingPongTrackController` | 新实现 `SingleTrackController` |
|---|---|---|
| 下一段何时准备 | 段末前 **1000ms**，在**备用播放器**上 | 段末那一刻，在**正在播放的播放器**上 |
| 准备内容 | `loadSlot` + `waitPrepared` + `seekSlot(0)` 完整就绪 | `reset()` + `openSync` + `fdSrc` + `prepare()` |
| 交接动作 | 换指针 + `play()`（O(1)） | 上面那串全部做完才可能出声 |
| 后果 | 换段无感 | 每次换源一段真实静音 |

旧文件已从工作区删除但仍在 git HEAD，可用
`git show HEAD:entry/src/main/ets/media/PingPongTrackController.ets` 复核
（`:61 standbyPrepareLeadMs = 1000`、`:62 handoffLeadMs = 20`、`:607 prepareStandbyForNext`、
`:654 handoffToStandby`）。

> 已按用户要求（**不要回到多 AVPlayer / PingPong**）单独调研，见
> `docs/预览播放器-跨段静音-方案调研.md`。结论：**不需要第二个播放器**——
> API 26 的 `AVPlayer` 自带播放列表（`addPlaybackMediaSource` / `advanceToNextMediaSource` /
> `advanceToMediaSource` / `onPlaybackContentChanged`），官方示例的换段流程**不调用 `reset()`**。
>
> **探针已真机跑完（第七份日志），结论：换条确实快 5 倍，但方案不采用。**
>

> |---|---|---|
> | 段交界耗时 | **322 / 323 / 340 / 377ms**（4 个交界） | **61ms**（1 次实测） |
> | 同会话 hevc 解复用失败 | **0 次** | **3 次**（2 次 prepare + 1 次 advance） |

> → 问题在**播放列表路径本身**，不在调用时机。
>
> **决定：开关 `USE_PLAYLIST_PROBE` 关回 `false`，线上保持已验证的 reset 路径。**
> 探针代码保留（含状态守卫 + 失败回落 + seek 看门狗），平台日后修复可重新验证。

| 轮次 | 现象 | 处理 |
|---|---|---|

| 修复 | 位置 | 作用 |
|---|---|---|
| **A. advance 前问状态** | `applyDesiredViaPlaylist()` | 状态不是 prepared/playing/paused/completed 就**不 advance**，等 `prepared` 事件再对账。这是死锁的直接原因 |
| **B. seek 前问状态** | 两条对账路径的 `issueSeek` 之前 | 播放器不接受 seek 就不发；发了必被拒且 `seekDone` 不来 |
| **C. seek 看门狗** | `releaseStuckSeekIfNeeded()` | `seekInFlight` 超过 1500ms 未完成就强制解卡 —— 保证**任何**丢失的 `seekDone` 都不会再锁死整轨。**reset 路径同样受益** |
| **D. 失败/报错兜底** | `abandonPlaylist()` | advance 连续失败 >3 次、或播放器进 `error`，立即退回 reset 路径。第七份日志里它自愈了 3 次 |

段交界处仍有 ~320ms 静音，这是**已知且被接受**的残留。

## 四、已排除的假设：seek 风暴

方案文档自己写过："每次 seek 都要冲刷解码器（听感 = 声音断断续续），且 seek 期间该轨不上报进度
（观感 = 进度条一顿一顿）"——症状对得上，所以先查过它，**结论是当前不成立**：

- `tools/sim-seek.mjs` 用**真实的 `checkSeek()`** 模拟"从轨与主轨实际完全同步、只有上报相位不同"：
  上报周期 ≤300ms 时 **60 秒内 0 次 seek**（最大观测偏差 = 周期本身）。
- SDK 确认 `timeUpdate` **默认每 100ms** 一次（`@ohos.multimedia.media.d.ts:3431`），
  远小于 `SEEK_TOLERANCE_MS = 300`。
- 主轨更不可能 seek：它的 `observedOffsetMs` 与 `wantedOffsetMs` 由**同一次上报**推出，偏差恒为 0。
- 真机日志里**稳态播放期间没有任何 `reason=drift` 的 seek**（第二份日志 58 秒全干净）。

结论：`checkSeek` 的容差策略在当前数据/节奏下不会形成风暴；但它仍违反设计文档的反目标 #4
（"严禁在正常连续播放过程中对从轨频繁调用 seekTo() 尝试微调"），属于潜在风险。

## 七、另外确认的缺陷

### 7.1 换段后第一次对账不 seek（会先播错位置约 0.7s）——真机确认

```
10:18:32.714 slot_0 seek(20058) reason=drift drift=-19307ms
```

`beginLoad`/`prepared` 都调 `resetSeekTracking()` → `lastSeekCheckAtMs = 0` → 第一次 `checkSeek`
的 `elapsedMs = 0` → 确认窗口永远凑不满 700ms → **即使目标偏移是 19s，第一次也判定"不 seek"
并直接 `play()`，从文件 0 位置开始播**，约 700ms 后才 seek 到正确位置。
影响：模板切换、行程加载、跳到**段中**位置的 seek —— 每次都会先出约 0.7s 的错位音画。

修法：刚载入/刚 prepared 时位置是**已知**的（就是 0），不是采样值，
此时若 `|0 - wanted| > SEEK_TOLERANCE_MS` 应**立即 seek**，不该走确认窗口。

### 7.2 出声轨选错了：**T4 预览没有声音** —— 已修

旧代码按**机位**选出声轨：`return camera === 'Front'`
（`git show HEAD:entry/src/main/ets/components/EditorPreviewArea.ets`，`isAudioMaster()` 内）；
新代码按**槽位下标**：`new SingleTrackController('slot_' + i, camera, i === 0)`
（`EditorPreviewArea.ets:131`）。而真实数据里**只有 front 文件有音频轨**。

**精确影响面**（按 `Models.ets` 的 `slotBindings` + `ffmpegPolicy` 逐个核对）：

| 模板 | 槽位顺序 | slot_0 | 导出是否有声音 | 预览 | 结论 |
|---|---|---|---|---|---|
| T1 防追尾双录 | Front / Rear | Front | `disableFrontAudio: false` | 有声音 | ✅ 正常 |
| T2 避险防加塞 | Front / Left / Right | Front | `false` | 有声音 | ✅ 正常 |
| T3 侧向防开门杀 | Left / Right | Left | **`true`** | 无声音 | ✅ **与导出一致，不是缺陷** |
| **T4 沉浸式旅拍** | **LeftFront / Front / RightFront** | **LeftFront** | `false` | **无声音** | ❌ **缺陷** |
| T5 单前视 | Front | Front | `false` | 有声音 | ✅ 正常 |

**T4 有 Front 视角**（`requiredCameras: [LEFT_FRONT, FRONT, RIGHT_FRONT]`，中间的 `center` 槽就是 Front），
而它按 `i === 0` 把唯一有音轨的 Front 轨**静音**、给没有音轨的 LeftFront **开音量**
⇒ 预览没声音、导出却有声音，两边不一致。

**修法（已实施）**：出声与否改为**按机位**判断，不再看槽位下标。

- `SingleTrackController.isAudioOutputTrack()` → `this.camera === 'Front'`；
- 构造函数去掉 `isAudioMaster` 参数（`EditorPreviewArea.ets:131` 同步改）；
- `setCamera()` 在机位**真的变化**时重新 `applyVolume()` —— 否则 T2→T4 切换会留下
  "该出声的没声、该静音的还在响"；
- T3 没有 Front 槽位 ⇒ 全部静音，与它的 `disableFrontAudio: true` 一致。

**顺带修掉的一个静默丢弃**：`applyVolume()` 原本在 `!prepared` 时**直接 return 且不记日志**，
一次音量意图就这么没了。现在会记日志（`音量=0/1（机位=… 出声轨=… 全局静音=…）` /
`音量跳过（player=… prepared=…）`），"某一轨没声音"以后一眼可查。

### 7.3 间歇性解码失败（最可疑的"间歇性断音"来源）

```
slot_1 state -> error
slot_1 player error: Unsupported Format: DEM_FMT_ERR-unsupport interface,
              unsupport container format type, hevc-
（error 分支清掉 loadingUri）→ 下一次对账重试 → prepare 成功 → 正常播放
```

同一个文件第一次载入报"不支持 HEVC"，重试即成功 —— **本身就是间歇性的**（三份日志里出现两次）。
若它落在**出声轨**（slot_0）上，就是一次真实的断音 + 重载（约 100~250ms 空洞）。
这条最符合"偶尔出现、现在又没了"的特征，**应作为首要嫌疑**继续观察。

### 7.4 一拖进度条就切声音

```
28.534 pause(3 轨) → 28.680 seek(18545) force → 28.688 play()
（日志里连续 4 次同样模式）
```

`Editor.ets` 的 `beginTimelineDrag()` 会把 `previewPlaying = false` → 三轨全部 `pause()`，
松手再 `play()`。**拖动期间声音必然被切断**，与设计文档"拖动期间完全不碰 player"不一致。

### 7.5 合并行程的显示与时长口径

合并行程的 `范围=16:58:56 - 15:12:47`（起始时间晚于结束时间，因为跨天），
而 `时长` 是各段之和（180s）—— 修好网格后，**时间轴与 UI 总时长终于一致**（都是各段之和）。

### 7.6 主轨的段边界事件是"死代码"（换段实际靠时钟，不靠 completed）

`GlobalTimelineManager.handleTrackBoundary()` 的设计意图是：

```
if (isMaster && segmentEndMs > clock) { clock.seek(segmentEndMs) }   // 主轨播完 = 这一分钟真过去了
```

但真机上这条分支**从未生效**，因为主轨的 `completed` 到达时 `loadedUri` 已被清空：

- 交界 2（第五份日志）：
  `11:06:12.741 slot_0 loading source: <第3段>` → `11:06:12.820 slot_0 state -> completed`
  → `segment completed:  end=0` → `boundary track=slot_0 master=true end=0` → `0 > 120000` 为假 → 空操作。
- 交界 1：`loading source:` 在 `12.542`，`state -> idle`（reset）在 `12.710`，
  主轨的 `completed` **根本没出现**（被 `reset()` 抢先吞掉）。

`completed` 分支用 `getCurrentSegmentIndex()` **反查 `loadedUri`**，而 `beginLoad` 会先清空 `loadedUri`；
主轨带音频轨、`completed` 又比静默轨晚 ~180ms 到（`12.820` vs `12.638`），于是必然踩中这个竞态。

**为什么现在无害**：换段实际由主轨自己的 `timeUpdate` 把时钟推过 60s/120s 触发
（`loading source:` 出现在 `12.542`，即 `slot_1` 报边界后 58ms），时钟是唯一权威，结果正确
（`漂移seek=0`）。

**为什么不能顺手"修好"**：若改成"载入时记下段下标、`completed` 时兜底取回"，
一旦 `completed(N)` 比 `prepared(N+1)` 晚到（实测只差 137ms：`12.820` vs `12.957`），
兜底值已经是 N+1 → `end` 会多出一整分钟 → `clock.seek()` **把进度条向前跳 60 秒**。
所以正确做法是**删掉这条分支**（让时钟继续当唯一权威），而不是给它补数据；
建议随 7.1 一起处理，不要在探针验证期间动它。

### 7.7 seek 被拒 ⇒ `seekInFlight` 永久卡住 ⇒ 整轨（含主轨）死锁 —— 真机确认

```
11:14:02.343  slot_0/1/2 seek(0) reason=playlist-force drift=0ms
11:14:02.344  slot_0 player error: Operate Not Permit: The current state is initialized,
              seek operation only support prepared/playing/paused/completed state.
11:14:03.219  用户点播放 → 此后没有任何 slot_0 play() / 上报节奏
```

`issueSeek()` 无条件把 `seekInFlight = true`，然后 `player.seek()`。若这次 seek 被播放器拒绝，
`seekDone` 不会触发，而**唯一的解锁点**就是 `seekDone` 回调或 `error` 分支：

- `reconcile` / `applyDesired*` 全部在 `if (this.seekInFlight && !forceSeek) return` 处返回
  → 永远走不到 `syncPlayState()` → **永不调 `play()`**；
- `timeUpdate` 处理里也有 `if (this.seekInFlight) return` → **不上报进度**；
- 若卡住的是**主轨**，时钟就完全不推进 → **整个预览"完全卡死、没有任何播放进度"**。

这不是探针独有的：reset 路径只是**恰好**因为"载入未完成时先 return"而躲过了它
（`if (this.loadedUri !== wantedUri) { beginLoad; return }`），并非免疫。

**修法**（已实施，见第三节 A~D）：① 发 seek 前先问状态；② `seekInFlight` 加 1500ms 看门狗。
真机上首次触发点是"模板应用后的首轮强制对账"（`forceSeek=true` 时容差检查必然要求 seek）。

### 7.8 视频 surface 必须在 `prepare()` 之前绑定 —— "第一组不显示主视角" —— 已修

用户口头报告（第七份日志那次测试，T2 + 三组合并行程）：

> 播放第一组不显示最上方的主视角；到 60s 切第二组可以显示主视角，但没有声音；
> 到 120s 切第三组，既有声音、视角也全面了。

代码里对得上的机制：

- `aboutToAppear()` → `applyTemplateAndTrip()` → 对账 → `beginLoad()` → `initialized` → `prepare()`；
  而 `initialized` 里绑 surface 的前提是 `this.surfaceId.length > 0`
  （`SingleTrackController.ets` 的 `initialized` 分支），此刻 XComponent 的 `onLoad` 往往**还没跑**；
- `SingleTrackView.ets:17` 的 `.onLoad()` 只在 `surfaceId` 非空且 `!== '0'` 时调
  `setSurfaceId()`，**否则静默跳过、没有重试、没有日志**；
- 于是第一段的 `prepare()` 是**在没有 surface 的情况下**完成的 → 画面不出来；
  等到 60s 交界 `reset()` 后重载，`initialized` 这次拿到了 `surfaceId`、在 `prepare()` 之前绑上 → 画面出现。
  这正是"第一组没有画面、切到第二组才出现"的形态。

**修法（已实施）**：把"surface 到手"变成载入的前置条件。

- 新增 `shouldWaitForSurface()`：`surfaceId` 为空就**不载入、不 prepare**，
  由 `setSurfaceId()` 触发的对账来驱动载入（reset 路径与播放列表路径都加了这道闸）；
- **必须有上限**：`SURFACE_WAIT_MAX_MS = 2000`，超时就"无 surface 载入"并打日志
  —— 万一某个槽位永远拿不到 surface，宁可只有声音，也不能整轨不载入；
- `setSurfaceId()` 增加日志：`收到 surface（首次=… 已prepare=… 已绑播放器=…）`
  —— 这是"surface 是否来晚了"的直接证据。

**注**：用户报告里"第二组没有声音"这一条，机制上更可能是**当时那个探针构建**的产物
（60s 交界处 slot_0 的播放列表 advance 成功后又报 hevc error，再经
`播放器进入 error，退回 reset 路径` 重载；从 error 状态出来的音频通路可能没恢复），
而探针已关闭。7.2 的音量日志可在下一次日志里直接证伪或证实这一点。
